# A5 — Mandatory-field metadata — is there any declared contract for a PAM request body?

**Scope:** OBJ-007 items 1, A5 and 9 · **Method:** static analysis plus retained run evidence
**HTTP requests issued:** 0 · **Database queries issued:** 0
**Reproduce:** `python tools\obj007_required_fields.py`
**Data:** `artifacts/analysis-data/required-fields.json` (5,940 rows) · `artifacts/analysis-data/required-fields-summary.json`

---

## 1. The verdict, stated first

**Mandatory-field metadata is effectively unavailable, and on the surface actually under test it is
entirely absent.** Not scarce — absent. Every candidate source was checked and none declares which
properties of a PAM request body are required, how long they may be, what format they take, or what
values they accept.

| Question a client must answer | Declared anywhere? | Count |
|---|---|---:|
| Which properties are mandatory? | ⛔ no | **0** of 5,175 |
| What is the maximum length? | ⛔ no | **0** of 5,175 |
| What format must the value take? | ⛔ no | **0** of 5,175 |
| What pattern must it match? | ⛔ no | **0** of 5,175 |
| Which values are permitted? | ⛔ effectively no | 7 of 5,175 (0.14%, and not endpoint-bound) |
| Is the property nullable? | ⛔ effectively no | 140 of 5,175 (2.7%) |

Of 5,175 body properties across 1,306 endpoints and 70 controllers, **4,904 (94.8%) carry no metadata
of any kind**. A further 264 (5.1%) are marked `INFERRED` — an inference this analysis made, not a
statement the product publishes.

### 1.1 The prior claim — re-derived independently, and confirmed

The brief (§5) states *"3 `[Required]` properties of ~6,738; no length, format or pattern validation
anywhere."* Both figures were re-derived from source by an independent scan of every `.cs` file in
`pam/PAM`. **Both reproduce exactly.**

| Figure | Prior | Re-derived | Verdict |
|---|---:|---:|---|
| `.cs` files scanned | 6,866 | **6,866** | ✅ confirmed |
| Public auto-properties (same regex as the prior scan) | 6,738 | **6,738** | ✅ confirmed |
| Public auto-properties (deliberately broader regex) | — | **6,845** | ✅ ratio only worsens |
| Properties carrying `[Required]` | 3 | **3** | ✅ confirmed |
| Coverage | 0.0445% | **0.0445%** | ✅ confirmed |
| Source characters scanned | — | 110.9 M | — |

**Provenance of the prior figure.** It originates in
`artifacts/loopholes/LH-10-no-validation-attributes-on-models/EVIDENCE.md` §1, generated by
`tools/lh_specs_static.py::_lh10_scan`. The same scan is quoted onward by
`docs/gaps/01-Data-Gap-Analysis.md` §2 and `docs/history/archive/document-agent-brief.md` §5. The `6,738`
denominator is a **property-occurrence count over `pam/PAM`**; `tools/SOURCE-MAP.md` §1
reports the same `3` against a different denominator (2,674 *distinct property names*), which is why
the two documents appear to disagree and do not.

The broader regex was run precisely to test whether `3 / 6,738` was an artefact of a tight pattern.
It is not: a pattern that also admits `{ get; }`, `protected`, `internal` and multi-line declarations
finds 6,845 properties and still **3** `[Required]`.

### 1.2 The material correction — on the surface under test the count is 0, not 3

This is the one place where the prior figure understates the problem, and it matters.

`6,738` is the auto-property population of **the whole .NET product**. It is not the request-model
surface of the API under test. `pam/PAM` implements only **48 of 1,306** catalogue endpoints (3.7%) —
the real API is served by separate microservices behind `ARCONAPIGateway` that are not in this
snapshot. So the denominator describes a body of code that is 96.3% *not* the thing being tested.

All three `[Required]` attributes sit in one file, on one class:

| File | Class | Property | Declared type |
|---|---|---|---|
| `ARCON_Services\ProvisioningService\ProvisioningDataAccessLayer\Models\Entity.cs` | `Request` | `targetHostType` | `MachineType` |
| same | `Request` | `rootUser` | `string` |
| same | `Request` | `rootpass` | `string` |

Measured against the catalogue:

| Check | Result |
|---|---:|
| Catalogue endpoints whose known properties include `targetHostType`, `rootUser` or `rootpass` | **0** of 1,306 |
| Controllers named `Provisioning*` among the 70 in the catalogue | **0** |
| Body properties on the surface under test with `is_required_declared = true` | **0** of 5,175 |

⛔ **The three `[Required]` attributes that exist bind to nothing under test.** They live on a
provisioning data-access class whose property names appear in none of the 5,940 mapped endpoint
properties. Quote `3 of 6,738` for the product; for the API being tested the honest figure is
**0 of 5,175**.

### 1.3 Twelve constraint families, zero occurrences

Every DataAnnotations and serialiser attribute that could constrain a request body was counted across
all 6,866 files. Twelve families return **zero**:

that the models enforcing it are in the microservices we were not given, not in `pam/PAM`.

## 2. Every candidate source, and what each actually declares

Five sources could in principle carry a mandatory-field contract. None does.

| # | Source | Could it declare required-ness? | What it actually declares |
|---:|---|---|---|
| 1 | `pam/PAM` C# models | yes, via DataAnnotations | 3 `[Required]`, **0 bound to the surface under test**; 12 constraint families at zero |
| 2 | Swagger specs (37 / 690 ops) | yes, via `required[]` | **0** — see §2.1 |
| 3 | Confluence export, 2,470 pp | only by example | field *names* and example values; never marks a field mandatory |
| 4 | Payload helpers (66 files) | no | bodies as currently sent — 111 of 217 creates, with hardcoded foreign keys |
| 5 | `APIConfig.java` | no | route, verb, controller, action only — no field information at all |

Two structural consequences of the field-name merge deserve stating plainly, because they bound how
far source 1 and source 3 can be trusted:

- **Types are name-matched, not endpoint-bound.** 3,689 of 5,175 body properties carry a C# type hint,
  but that type comes from *a class somewhere in the product with a property of the same name* — not
  from the endpoint's actual request model. It is a hint, never a contract. Every row records this in
  `declared_type_basis`.
- **Confluence payloads bind by page proximity.** A binding can simply be wrong, so the 40 properties
  inferred required from documentation frequency are graded `WEAK` in the data, not `OBSERVED`.

### 2.1 Swagger declares no required property on any operation validated

The 37 specs are listed in `data/sources/Automation PAM Endpoints Details_Shared(Swagger_JSON
Links).csv` but are **not cached locally** — `Reports/SpecCache/` does not exist, and fetching one
needs network access, which A5 is forbidden. The retained validation run is therefore the only
available evidence of what those schemas declare, and it is decisive:

| Measure | Value |
|---|---:|
| Operations validated (`artifacts/runs-archive/Evidence/swagger-devint/`) | 102 |
| `L4_required_fields` verdict = `NA` | **102 of 102** |
| Distinct `L4` notes | **1** — `"schema declares no required properties"` |

Every operation, without exception. Combined with the prior finding that **0 of 690** operations
declare any 4xx or 5xx, the developer-supplied schemas describe request and response *shapes* with no
required properties and no failure modes. They are also a **different surface** — ~6% name overlap
with the catalogue — so even a fix there would not cover the API under test.

## 3. What *is* known — and why it is not a substitute

The absence is not total. It is just not a contract.

| Grade | Count (of 5,175 body properties) | What it means |
|---|---:|---|
| `DECLARED` | **7** (0.14%) | An enum member list recovered by matching a C# enum type name. Not endpoint-bound |
| `INFERRED` | **264** (5.1%) | 224 the server named in a rejection (§4) + 40 present in every documented example |
| `ABSENT` | **4,904** (94.8%) | No source says anything about this property |

And 697 of 1,306 endpoints (53.4%) have **no known properties at all** — not one source names a single
field for them. For those, even the property list is unknown, let alone which fields are mandatory.

## 4. The only real mandatory-field source is error prose

The server knows exactly which fields are mandatory. It publishes that knowledge in one place: the
text of a rejection. Mined from `artifacts/runs/2026-07-29_181439/results.json`:

| Measure | Value |
|---|---:|
| Endpoints that revealed at least one mandatory field | **126** |
| Distinct property names revealed | **37** |
| Distinct rejection messages | 41 |
| Body properties thereby known mandatory | **224** |
| Range constraints that leaked into prose | 21 (all `PageSize > 0`) |

**Five different message grammars** carry the same fact, which is itself evidence that no single
declarative rule backs any of them:

| Grammar | Example | Occurrences |
|---|---|---:|
| JSON deserialiser | `Required property 'UserId' not found in JSON. Path '', line 1, position 2.` | 123 |
| Procedural check | `Validation error occurred - UserName is Mandatory` | 64 |
| Bare `is required` | `PageSize is required should be greater than 0.` | 30 |
| ASP.NET model state | `The HSMLabel field is required.` | 8 |
| Null check | `DisplayName cannot be null.` | 3 |

⚠️ **Even this recovered set is unreliable for generation, because the names are not canonical.** The
37 revealed names include `UserId`, `UserID` and `UsrId`; `LOBId` and `LOBID`; `ServiceId`,
`ServiceID` and `Service_ID`; `ServiceUserName` and `Service_Username`. A generator cannot tell
whether these are the same field spelled inconsistently or genuinely different fields.

Three further limits make prose a poor contract substitute:

1. **It is discoverable only by failing.** You must send a bad request to learn the rule — which on
   this API means a mutating call you may not be permitted to replay.
2. **It is partial.** 126 of 1,306 endpoints revealed anything. The other 1,180 stayed silent.
3. **The rule text is not stable.** `PageSize is required should be greater than 0.` and `PageSize is
   required and should be greater than 0.` are the same rule in two spellings, from the same run.

Two endpoints deserve note as precedent: `GET /api/Service/ServiceMandatoryFields` already exists in
the surface, and `PageSize > 0` proves the product *can* express a bound. The capability is there; it
is simply not declared.

## 5. Impact on Create APIs — one root cause at three layers

### 5.1 The create-endpoint metadata figure

| Measure | Count | Share of 217 |
|---|---:|---:|
| Create endpoints in the catalogue | **217** | 100% |
| …with at least one property known from any source | 151 | 69.6% |
| …with **zero** properties known from any source | 66 | 30.4% |
| …with **any** mandatory-field metadata at all | **32** | **14.7%** |
| …with any **declared** mandatory metadata | **0** | **0%** |
| …whose mandatory set is known only from server error prose | 29 | 13.4% |
| …with **no mandatory-field signal whatsoever** | **185** | **85.3%** |
| Create body properties with a max-length / format / pattern | **0** of 1,245 | 0% |

**For 185 of 217 create endpoints there is no way to know which fields are mandatory before calling
them.** For the 32 that have a signal, 29 of those signals were extracted from rejection messages,
not read from a contract.

### 5.2 The causal chain, and exactly how far the evidence supports it

The same root cause surfaces as three different numbers at three layers:

| Layer | Measured figure | Source |
|---|---|---|
| **Contract** | 0 of 5,175 body properties declared mandatory; 0 of 217 creates with declared mandatory metadata | this analysis |
| **Execution** | **13 of 217** creates produced an insert-success message (6.0%) | `results.json`, re-derived |
| **Chaining** | **196** L5 failures, every one `resolved []; MISSING ['NEW_ID']` | `results.json`, re-derived |

The mechanism is not in dispute:

```
no declared mandatory set
  -> a generated create payload cannot be known-valid before it is sent
     -> the create is rejected                        13 of 217 succeed
        -> a failed create returns no identifier
           -> the chain cannot resolve NEW_ID         196 x MISSING ['NEW_ID']
              -> the flow stops at hop 1
                 -> nothing exists to read back       L6: 2 PASS / 105 FAIL
```

### 5.3 The 196 chain failures are not a harness artefact — measured

The obvious counter-argument to the chain above is that the harness simply failed to find identifiers
that were present. That has been tested and **excluded**. The 196 `MISSING ['NEW_ID']` failures split
by root cause as:

| Root cause of the 196 L5 failures | Hops | What it establishes |
|---|---:|---|
| (a) The create genuinely failed — no identifier ever existed | **117** | The payload was rejected. Nothing could have been extracted |
| (b) The create was acknowledged but returned no identifier | **19** | Even a "successful" create publishes no id to chain from |
| (c) **Extractor bug — an identifier was present and missed** | **0** | ⛔ **Excluded.** Two searches far wider than the extractor found no identifier anywhere in any of the 196 responses |
| (d) Indeterminate | 60 | Insufficient evidence to classify either way |

**Cause (c) being zero is the decisive result.** The chain does not break because the harness is weak;
it breaks because creates fail (117) or, when they do not fail, return nothing usable (19). Causes
(a) and (b) together account for **136 of 196** with the remaining 60 unclassified — and neither is a
tooling defect. Cause (a) is exactly the failure mode the metadata gap produces: a payload that cannot
be known-valid before it is sent.

Cause (b) is a second, independent defect worth separating: 19 hops had a create the server
acknowledged, yet the response carried no identifier for the created record. No amount of
mandatory-field metadata fixes that one — it needs the create responses to return the id they
created. It is called out as `A5-09`.

### 5.4 Where the evidence is direct, and where it is not

This must be stated precisely rather than asserted wholesale. Taking the L4 message-semantics check on
create endpoints only — 213 of the 217 were called:

| Create-side L4 outcome | Hops | Reading |
|---|---:|---|
| `FAIL` — server **named** a missing or required property | **31** | Direct evidence of the metadata gap |
| `FAIL` — server stated **no cause** | **150** | Cause undiagnosable from the response |
| `PASS` — message asserts an insert | 15 | Succeeded |
| `PASS` — message asserts no write (e.g. `Operation Successfull`) | 19 | Outcome unknown |

So: the metadata gap is **directly evidenced 31 times**, and it is the largest *diagnosable* failure
class. It is **not** the sole cause of all 196 L5 failures — 7 create hops returned `No HTTP resource
was found that matches the request` (catalogue drift, LH-05) and 2 returned `Already Exists`
(a no-op, not a validation failure).

The 150 "cause not stated" failures are the sharper point. With no declared contract, **you cannot
tell whether the payload was wrong or the endpoint was broken.** The absence of metadata both causes
failures and removes the means to diagnose them. That is why the L5 count (196) exceeds what the
named-cause evidence alone would license, and why the chain above is stated as the mechanism the
evidence supports rather than as an arithmetic identity.

⚠️ **One definitional caveat on the 13.** The published figure counts create endpoints whose success
message contains `insert`. A reading that also credits `Record Added successfully.` — which asserts an
insert in different words — gives **15**. The difference is definitional, not a measurement error.
**Quote 13** for consistency with `Reports/` and the loophole packs; 15 is recorded in the summary
JSON. Neither reading changes the conclusion that ~93% of creates cannot be driven.

## 6. Impact on downstream validation — what cannot be asserted

### 6.1 You cannot author a truthful "missing mandatory field" test

The test requires knowing which field is mandatory. That knowledge exists for 224 of 5,175 body
properties (4.3%), and every one of those 224 came from a rejection message rather than a contract.
For the remaining **4,951 properties, optionality is unknown — not confirmed**. Omitting one and
asserting a rejection would be asserting a guess.

### 6.2 Boundary, format and pattern tests are guesses by construction

| Negative scenario class | Scenarios possible | Authorable | ⛔ Unassertable | Why |
|---|---:|---:|---:|---|
| Missing mandatory field | 5,175 | 224 | **4,951** | Mandatory-ness known only where the server already complained |
| Boundary / max length | 5,175 | 0 | **5,175** | `[StringLength]`/`[MaxLength]`/`[MinLength]` occur 0 times — there is no boundary to probe |
| Invalid format | 5,175 | 0 | **5,175** | `[DataType]`/`[EmailAddress]`/`[Phone]`/`[Url]` occur 0 times |
| Invalid pattern / enum | 5,175 | 7 | **5,168** | `[RegularExpression]` occurs 0 times; 7 enum matches are not endpoint-bound |
| **Total** | **20,700** | **231** | **20,469** | **98.9% unassertable** |

This is a **derived scenario space**, not a count of tests that exist: the four standard
property-level negative classes applied to every known body property. The length class is applied to
all 5,175 rather than to string properties only, because declared types are themselves absent or
merely name-matched — **the surface cannot even be scoped to its string fields.**

### 6.3 The existing negative corpus cannot assert application behaviour

Re-derived from `Automation gitlab repo/pam_automation_bootstrap/testdata/Negative_API_Automation_Test_Input_Data.xls`:

| Measure | Value |
|---|---:|
| Sheets | 76 |
| Header blocks | 151 |
| Data rows | **3,167** |
| `ExpectedStatus = 405` — the web framework rejecting a verb | 1,604 |
| `ExpectedStatus = 401` — the auth layer | 1,550 |
| `ExpectedStatus = 200` — the application's own validation | **13** |
| Blocks carrying an `ExpectedErrorCode` column | **0 of 151** |
| Rows carrying an `ExpectedErrorCode` | **0** |

**3,154 of 3,167 rows (99.6%) never reach application code.** They confirm that IIS and the auth
middleware work. Only 13 rows target the application's own validation, and **all 13 are
unassertable**: PAM signals a rejection as HTTP 200 with an `errorCode` in the body, so a row whose
only expectation is `ExpectedStatus = 200` passes whether the request was correctly rejected or
wrongly accepted. It cannot tell the difference.

The `ExpectedErrorCode` column does not merely go unpopulated — **it is absent from all 151 header
blocks.** The framework parameter exists
(`validateApiResponseWithResponseTime_ExcelBasedsettingnegative(...)`); the data schema to feed it
does not.

⚠️ **Row-count reconciliation.** `docs/gaps/01-Data-Gap-Analysis.md` §2 states 3,317 parsed
rows. That total includes the 150 header rows of the dominant layout (3,167 + 150 = 3,317). The
`405 / 401 / 200` split re-derives as **1,604 / 1,550 / 13 — identical** to the prior figure, so no
conclusion changes. Quote **3,167** as the data-row count. The `3,652` in that file's basis line is a
third, unreconciled number.

### 6.4 The answer to "how many negative scenarios are unassertable"

| Sense of the question | Answer |
|---|---:|
| Existing rows targeting application validation that cannot be asserted | **13 of 13** (100%) |
| Existing rows that test transport/auth instead of the application | 3,154 of 3,167 (99.6%) |
| Property-level scenarios in the derived space that cannot be authored truthfully | **20,469 of 20,700** (98.9%) |
| Create endpoints for which no missing-mandatory test can be written at all | **185 of 217** (85.3%) |

## 7. Risks — what ships untested, and what a consumer cannot know

| # | Risk | Exposure |
|---:|---|---|
| 1 | **No server-side model validation runs.** With 12 constraint families at zero occurrence, every check is hand-written per action | A forgotten check is invisible. There is no declarative rule to review, so review cannot catch the omission |
| 2 | **No length bound is declared anywhere on the surface** | Over-long input is untested on 5,175 properties. Truncation, overflow and storage-layer errors are unexercised |
| 3 | **No format or pattern is declared** | Email, IP, hostname, date and identifier formats are unvalidated and untested. `ServiceIP` is known mandatory but has no declared format |
| 4 | **93% of create endpoints cannot be driven** | Write paths, and every read-back and teardown depending on them, ship unexercised. Only **2** writes in 1,868 calls were proven to have persisted |
| 5 | **Negative testing validates the web server, not the product** | 99.6% of the negative corpus. A regression in application-level input validation would not be caught |
| 6 | **A rejection and an acceptance are indistinguishable to a test** | HTTP 200 + `errorCode`, with no error-code register and no `ExpectedErrorCode` in the data. Wrongly-accepted bad input passes silently |
| 7 | **Every consumer rediscovers the same rules empirically** | 126 endpoints' mandatory sets were recovered by reading rejections. Each new client repeats that cost, and each may infer differently |
| 8 | **Inconsistent field naming corrupts what little is known** | `UserId` / `UserID` / `UsrId` on the same surface. A consumer cannot tell a spelling variant from a distinct field |
| 9 | **Nothing can be generated** — docs, clients, SDKs, validators | No metadata exists to render. This is why 70% of endpoints are undocumented and stay that way |
| 10 | **The gap is invisible in reporting** | `3 of 6,738` reads as "almost none". The surface-scoped figure is **0 of 5,175** — none |
| 11 | **Even an accepted create publishes no identifier** | 19 of 196 chain failures. A consumer cannot learn what it just created, so it cannot verify, update or delete it — independent of the metadata gap |
| 12 | **The blockage is confirmed to be in the product, not the tooling** | Extractor bugs account for **0** of 196. Any remediation plan that targets the harness rather than the API will not move these numbers |

## 8. Recommendations

Each carries a recommended and an alternative solution. Effort is T-shirt size plus a rough
person-day range. Full structured form: `data/analysis/solutions-A5.json`.

### A5-01 · No declared mandatory-field metadata on the surface under test — **Critical**

| | Recommended | Alternative |
|---|---|---|
| **Solution** | Annotate request models with `[Required]` in the gateway microservices and enable model-state validation in the pipeline, **creates first** (1,245 properties across 217 endpoints) | Generate and publish an OpenAPI document from the live gateway microservices, with `required[]` populated |
| **Advantages** | Turns metadata into enforced behaviour; one change fixes validation, docs and test generation together; incremental and shippable per controller | No change to product code; machine-readable for every consumer; covers endpoints whose source we were never given |
| **Disadvantages** | Touches many services; enabling model validation may reject payloads existing clients send today, so it needs a compatibility pass | Documentation only — nothing is enforced server-side, so the doc can drift from behaviour |
| **Effort** | **L** — 15–30 person-days | **M** — 10–20 person-days |

### A5-02 · No length, format, pattern or range metadata anywhere — **High**

| | Recommended | Alternative |
|---|---|---|
| **Solution** | Add `[StringLength]`, `[Range]` and `[RegularExpression]` derived from the existing database column definitions, which already encode length and type | Publish a data-dictionary export (table, column, type, length, nullability) and let the harness derive boundaries from it |
| **Advantages** | The constraints already exist in the schema — this publishes them rather than inventing them; enables boundary testing on 5,175 properties at once | Very cheap; needs no product-code change; immediately unlocks boundary-test generation |
| **Disadvantages** | DB column length is not always the API contract; mapping column to property is manual where names differ | Not enforced; the API can still accept what the DB will reject, which is the current defect restated |
| **Effort** | **L** — 20–40 person-days | **S** — 3–5 person-days |

### A5-03 · Mandatory-ness is discoverable only by failing, in five prose grammars — **High**

| | Recommended | Alternative |
|---|---|---|
| **Solution** | Return a structured field-level error: `{errors:[{field, rule, message}]}`, replacing all five prose grammars | Expose a describe endpoint per operation returning its required fields, types and bounds — `GET /api/Service/ServiceMandatoryFields` already exists as precedent |
| **Advantages** | Removes prose parsing entirely; makes negative assertions exact; fixes LH-04 in the same change | Discoverable without sending a bad request; no change to the validation path; a working pattern already ships |
| **Disadvantages** | Response-shape change — existing clients parsing message text will break; needs a version or feature flag | A second source of truth that can drift from enforcement unless generated from the same models |
| **Effort** | **M** — 8–15 person-days | **M** — 10–18 person-days |

### A5-04 · 185 of 217 create endpoints have no mandatory-field signal — **Critical**

| | Recommended | Alternative |
|---|---|---|
| **Solution** | Ask the developers for one known-good request body per create endpoint, captured from their own integration tests | Build a curated fixture library in the harness from the 224 observed-mandatory properties plus the 1,654 documented payloads, and grow it by differential probing |
| **Advantages** | Cheapest route to the largest coverage gain; developer time is minutes per endpoint; a real payload settles mandatory-ness, types and valid values at once | Needs nothing from anyone else; starts from evidence already retained; compounds as more creates succeed |
| **Disadvantages** | Depends on another team's schedule; a fixture is a sample, not a contract, and goes stale silently | Slow; encodes current behaviour including defects; probing means sending mutating calls, which the safety rules restrict |
| **Effort** | **S–M** — 5–10 person-days (mostly developer time) | **M** — 10–18 person-days |

### A5-05 · Negative testing is structurally unassertable — **Critical**

| | Recommended | Alternative |
|---|---|---|
| **Solution** | Publish the error-code register and add an `ExpectedErrorCode` column to the negative data schema — the framework parameter is already plumbed and the column is missing from all 151 blocks | Freeze a differential baseline: observe each rejection once, record status + errorCode + message, and assert against the frozen value |
| **Advantages** | Converts 13 unassertable rows into real assertions and unblocks thousands more; catches "should have been rejected and was not" | Available immediately with no product dependency; detects any future change in rejection behaviour |
| **Disadvantages** | Needs the register, which does not exist — 4 codes documented against 108 observed | Locks in current behaviour as correct, defects included; cannot detect input that should be rejected and never was |
| **Effort** | **S–M** — 5–10 person-days | **S** — 3–6 person-days |

### A5-06 · The published metric understates the gap — **Medium**

| | Recommended | Alternative |
|---|---|---|
| **Solution** | Re-scope the metric to the surface under test and publish **0 of 5,175** alongside `3 of 6,738`, stating that the three bind to no tested endpoint | Obtain the gateway microservice sources so the denominator describes the API actually under test |

| **Disadvantages** | Reporting change only — fixes no behaviour | Access and coordination dependency; 96.3% of the surface is currently outside the snapshot |

### A5-07 · Field names are not canonical, so even the observed set is unreliable — **Medium**

| | Recommended | Alternative |
|---|---|---|
| **Solution** | Publish a canonical field-name registry and accept the historical spellings as explicit serializer aliases | Normalise case and separators in the harness only, and treat `UserId`/`UserID`/`UsrId` as one logical field |
| **Advantages** | Fixes the ambiguity for every consumer, not just this test suite; makes generated code and docs coherent | Cheap, entirely within our control, already partly implemented via case-insensitive matching |
| **Disadvantages** | Touches many services; aliases must be kept forever for compatibility | Does not fix the API — a real consumer still cannot tell a variant from a distinct field; risks merging two genuinely different fields |
| **Effort** | **M** — 8–15 person-days | **XS–S** — 1–3 person-days |

### A5-09 · Acknowledged creates return no identifier — **High**

Separated from A5-01 because **no amount of mandatory-field metadata fixes it**: 19 of the 196 chain
failures had a create the server accepted, whose response carried no id for the created record.

| | Recommended | Alternative |
|---|---|---|
| **Solution** | Return the created record's identifier in the create response — `{Success, Message, Result:{Id}}` — for all 217 create endpoints | Have the harness resolve the identifier with a follow-up read, matching on the values just submitted |
| **Advantages** | The standard create contract; unblocks chaining and read-back for every consumer, not just tests; removes a whole class of guesswork | No product change; works with endpoints as they ship today |
| **Disadvantages** | Response-shape change across 217 endpoints; needs a version or feature flag for existing clients | Fragile and sometimes impossible — LOB names are AES-encrypted at rest, so matching a created record by the name submitted cannot work; adds a call per create |
| **Effort** | **M** — 10–20 person-days | **S–M** — 5–12 person-days |
